# Release notes — 2026-09-15

These notes describe the changes in this cut and the verification that was
completed. The application build, the private relay policy and the reviewed
KubeJS generator compatibility were deployed together on 2026-09-15 and then
verified against the running system. The sections below separate what was
verified from what remains limited.

## Server control and UI

- **Update fence.** While any profile holds a live update, every Start
  entrypoint stays paused so a second lifecycle action cannot race the updater.
  The running server keeps its own controller-side fence.
- **Honest readiness copy.** The server rail reports `Offline` when a profile is
  stopped, `Updating…` while an update is in progress, and the readiness text
  (`Ready on required ports`, or `Accepted; waiting for readiness`) only when
  the profile is genuinely starting. An updating or stopped profile is never
  shown as "accepted".
- **Offline history.** A stopped profile keeps its most recent retained run
  available for the history view and labels the window truthfully, including
  the multi-run 24 h label. Offline time is never plotted as zero activity.
- **Mobile and startup baseline.** Drawer navigation, touch scrolling and the
  startup-settings panel work within the viewport, and learned startup
  estimates synchronize across tabs, persist across navigation and reload, and
  are recovered from fresh status after a resume.

## Modpack packaging

- **Reviewed KubeJS compatibility guard.** Staging refuses to modify the
  gym-loot generator unless the generator bytes match a reviewed revision, the
  artifact version is one the transform is bound to, and all baked reward
  tables match the reviewed generator output. The reviewed record is the single
  authority: a manifest that declares its own path, statement, replacement,
  digests, version allowlist or reward set is refused, naming the differing
  fields. Unreviewed inputs fail closed and leave every byte untouched.

## Public relay recovery

- **Automatic clean-exit recovery.** The fenced Minecraft Bore client carries a
  paced restart policy, so an unexpected exit — including the clean exit a
  dropped or rebooted remote relay produces — is restarted without operator
  action. Retries stay paced by a fixed interval, and the start rate limit is
  disabled so a long remote outage cannot strand the unit in a failed state.
- **Intentional stop is still intentional.** `systemctl stop` (and
  `disable --now`) suppress every restart. A bare `disable` does not stop a
  running client, and the unit has no `[Install]` section. Removing the arm
  marker gates later starts; it does not terminate a client that is already
  running. The liveness helper still only restarts an already-active client and
  keeps its ownership, half-open and cooldown checks. See
  [operations example](../operations-example.md).

## Diagnostics

- **Timestamped, bounded capture.** Stall diagnostics produce timestamped,
  size-bounded evidence with an in-memory cursor, an appended record mode that
  is created `0600`, single-linked and `flock`-guarded, a byte cap on error
  lines, and terminal failure reporting when an output cannot be written.
  Nothing here reads or stores player identity, private messages or raw packet
  payloads.

## Backups

- **Monitoring.** Laptop-backup collection exposes metrics and alert rules
  (validated with `promtool`) so a stale or failing collector is visible
  promptly.
- **Preview-only retention.** Retention planning is a preview: it reports what
  would be pruned and preserves the local protections, and it never deletes
  archives on its own. Catalogued payloads require the retirement operation,
  which records a typed, append-only ledger.
- **Quarantine fetch scope.** Recovery tooling refetches a quarantined payload
  only through the reviewed recovery path, and the ledger's terminal states are
  preserved across offline state migration.

## Verification performed

- **Deployed verifier:** 59/59 checks pass against the running application.
- **Test suites:** Python 3.11 and 3.12 each report 2180 passed, 4 skipped; the
  browser suite reports 172 passed.
- **Offline browser run:** the server rail shows Players/Uptime/Health as
  `Offline` for a stopped profile, the manual update check reports the current
  version, and no generic Apply control is offered.
- **Mobile browser run:** drawer scrolling stays within the viewport, the
  startup-estimate preference survives navigation and reload, and two tabs
  synchronize in both directions. The harness forwarded no lifecycle
  mutations.
- **Offline history:** after the test server returned to standby, a live mobile
  check verified historical CPU/memory labels, the bounded multi-run time range,
  and Offline player/uptime labels without fabricated zero samples.
- **Relay recovery:** the fenced relay restarts automatically after an
  unexpected exit and stays down after an intentional stop, with the arm
  marker, sandbox and local wake proxy unchanged.
- **Startup:** one controller-owned start reached Ready with no reloads and a
  single Start request; the fifth learning sample completed, so the next
  natural start is eligible for a numeric estimate.
- **Script loading:** 125/125 startup and 239/239 server script loads completed
  with no script errors or read-only-filesystem errors.
- **Backups:** the laptop metric service and timer are installed and active, and
  the added rule set loads and passes `promtool` (96 rules, 6 files) with a
  successful reload. A real quarantine fetch was size- and checksum-verified.
  Retention remains report-only: no deletion was proposed or executed.

## Remaining limits

- Numeric startup estimates begin only after five successful starts for a
  profile/version. The fifth sample is now recorded; numeric display still
  awaits the next natural start.
- The browser runs used a bounded harness with heartbeat-substituted events.
  Human single-sign-on and the native event stream were not exercised.
- Coincident young-GC pauses were observed at the two longest stall windows but
  do not account for the whole stall; the rare-stall root cause remains open and
  the autosave hypothesis is unproven. A bounded capture window that overlapped
  startup/idle time is not a human-gameplay sample.
- The missing modpack registry/tag messages in the server log are third-party
  content warnings, not script failures. The logs are not claimed fully clean.
- The backup laptop has capacity available, but the virtualization host's root
  filesystem remains low on free space and needs separately scoped attention.
